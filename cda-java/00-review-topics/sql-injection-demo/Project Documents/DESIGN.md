# DESIGN — SQL Injection Demo (Spring MVC)

A deliberately-insecure "Widget Store" web app for teaching SQL injection in a
safe, isolated sandbox. A product **search box** builds its SQL by string
concatenation, so the same box can **read** data from other tables (`UNION`) and
**vandalise** data (stacked `UPDATE`/`DELETE`/`DROP`). It uses the layered
architecture the students already know and runs against a throwaway `sqli_demo`
Postgres database of fake data.

---

## Libraries & frameworks

| Library | Why it's here |
|---------|---------------|
| **Spring Boot** | Configuration, dependency injection, startup. |
| **Spring MVC** (`spring-boot-starter-web`, embedded Tomcat) | Serves the static web page and the REST endpoints (`/api/search`, `/api/login`). |
| **Spring JDBC** (`JdbcTemplate`) | The data-access API the students use. The vulnerable path hands it concatenated SQL; the secure path (`searchSecure`) hands it a parameterized `?` query — toggled live on the page. |
| **PostgreSQL JDBC driver** (runtime) | Talks to the `sqli_demo` database. |

No ORM and no security framework — those would hide the mechanism. The front end
is a single static HTML page with a little vanilla JavaScript (`fetch`); no
build step or JS framework.

## How the pieces fit

```
index.html (browser)
   │  fetch GET /api/search?q=…           fetch POST /api/login
   ▼                                      ▼
ProductController ──► ProductService ──► ProductRepository ─┐
AuthController    ──► AuthService    ──► UserRepository    ─┤
                                                           ▼
                                        JdbcTemplate ──► PostgreSQL (sqli_demo, schema app)
```

- The **controller** returns, alongside the data, the SQL for whichever path ran
  — the concatenated string (which *is* what executed) in vulnerable mode, or the
  `?` template plus the bound value in Secure mode. So the page's printed SQL is
  accurate in both modes, not a separate preview that could drift from reality.
- A `secure` request flag (the page's **Secure mode** switch) selects
  `searchSecure()` so the fix can be demonstrated live against the same payloads.
- The **service** does nothing to the input — it demonstrates how untrusted text
  travels "blindly" through a layered app when no layer validates or parameterizes.
- The **repository** is where the SQL is built by concatenation. It is the one
  place the fix (a `?` parameter) needs to go.
- The **front end** calls the REST endpoints and renders the SQL, the result
  rows, and — for a `;`-stacked write — a notice explaining that the extra
  statement already executed.

## Deliberate insecurities (the teaching surface)

| What | Where | Why |
|------|-------|-----|
| Concatenated SQL | `ProductRepository`, `UserRepository` | The injection itself |
| Clear-text passwords | `schema.sql`, `User` | Makes a `UNION` read an instant disaster |
| No keys/constraints | `schema.sql` | Realistic of hastily-built apps; nothing blocks mass `UPDATE`/`DELETE` |
| Table-owning DB account | `.env` → `sqli_owner` | So stacked `UPDATE`/`DELETE`/`DROP` actually run in the demo |

**Safety** does not come from the app — it is a *contained lab*, via three layers:

1. **Isolated data** — a throwaway `sqli_demo` database of fake data, reset in one
   command (`schema.sql`).
2. **Non-superuser account** — the app connects as `sqli_owner`, which *owns* the
   two demo tables (so vandalism works) but is **not** a superuser, so a stacked
   payload can't run OS commands (`COPY … TO PROGRAM`), read server files, or read
   `pg_authid`. It's confined to those two tables.
3. **Localhost binding** — `server.address=127.0.0.1`, so the vulnerable endpoints
   aren't exposed to the network.

This is deliberately over-privileged *within* those two tables, and safe only
because of the three layers above — not a claim that "nothing real is reachable."

## Feature summary

- **Product search** (`/api/search`) — normal search; `UNION` read of the users
  table; stacked `UPDATE`/`DELETE`/`DROP` vandalism. Shows the executed SQL and
  the database's response every time.
- **Staff login** (`/api/login`) — clear-text check; used to prove stolen
  credentials are real (and that overwriting them via the search box works).
- **Example-payload buttons** on the page so the instructor runs attacks without
  typing.
- **Secure mode switch** — re-runs the same payloads through the parameterized
  path (`searchSecure`), so the fix is shown live: the attacks return nothing and
  change nothing.
