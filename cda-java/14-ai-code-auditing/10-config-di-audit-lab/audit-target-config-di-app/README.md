# Audit Target: Customer Portal (Configuration + DI)

This is a small Spring Boot customer-portal service generated by an AI assistant.
It builds and boots cleanly, and it passes a single-user smoke test. Your job is
to decide whether it is *safe to deploy* — running the **configuration security
checklist** and the **four-step DI-audit pass** together, as one audit, over the
whole artifact.

## What is here

- `pom.xml` — Spring Boot web / security / actuator app.
- `src/main/resources/application.yml` — the application, datasource, JWT,
  notifier, logging, and actuator configuration.
- `src/main/java/com/acme/portal/` — the security and notifier wiring, the
  controllers, the user repository, the token and audit services, and the
  per-user state holder that read from that configuration.

## Your task

Run **both passes together** and produce one findings report. Do not stop at the
first thing that looks wrong, and do not treat the config files and the wiring as
two separate reports — they are one audit.

1. **Config pass first.** Walk every config file and key against the checklist —
   secrets, insecure defaults, overly permissive settings, environment, and
   framework. Record each finding as you go. Verify any key that *looks* like a
   security control against the framework's real property list before you trust
   it.
2. **DI pass second.** Enumerate every binding the container wires — each
   `@Component`, `@Service`, `@Repository`, `@RestController`, and each `@Bean`.
   For each, trace provenance (where does the implementation come from, and who
   controls that input?), check scope (does the bean's lifetime match the state
   it carries?), and verify boundaries (what can each injected dependency
   *reach*, versus what its role warrants?).
3. **Reconcile across layers.** For every binding whose provenance you traced,
   check whether it resolves from a value the config pass already flagged. Each
   such intersection is a **cross-layer** finding — the class that looks clean
   under either pass alone. Log it once, with both locations.
4. **Coverage check.** Scan your report for any vulnerability class with zero
   findings and confirm you cleared it deliberately, not by oversight.

For every finding record: **location** (file and key, or class and binding),
**defect class**, the concrete **risk** (the exploit, with who reaches it and
what they gain), and a **recommended fix**.

You are graded on the audit method and the completeness of the report —
location, risk, and fix for each finding — not on the raw count of flaws found.

There is no answer key in this folder. Produce your findings on your own.
